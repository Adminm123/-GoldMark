# GoldMark V2 — ข้อกำหนดระบบป้องกันทุจริตการรับซื้อทองเก่า
เวอร์ชันเอกสาร: 1.0  
สถานะ: ข้อกำหนดสำหรับออกแบบและพัฒนา — ยังไม่ใช่ระบบใช้งานจริง  
ขอบเขต: แยกจากต้นแบบ V2 และห้ามเชื่อมการคำนวณทดลองกับธุรกรรมจริงโดยไม่ได้รับอนุมัติ

## 1. เป้าหมาย
ลดความเสี่ยงที่พนักงานแจ้งราคาซื้อทองเก่าต่ำกว่าราคาที่ระบบควรคำนวณ แล้วเก็บส่วนต่าง พร้อมให้สำนักงานใหญ่ตรวจสอบได้ทุกสาขาจากหลักฐานส่วนกลาง

เป้าหมายควบคุม:
- ราคาที่ลูกค้าเห็นต้องผูกกับผลคำนวณและราคากลางเวอร์ชันที่ใช้อ้างอิง
- การประเมินทุกครั้งต้องมีร่องรอย แม้ลูกค้าไม่ตกลงขาย
- การแก้ไข ยกเลิก และยืนยันธุรกรรมต้องตรวจย้อนหลังได้
- เปรียบเทียบยอดประเมินกับยอดจ่ายจริงได้
- ไม่เปลี่ยนสูตรคำนวณทองเก่าปัจจุบันโดยไม่มีการอนุมัติและทดสอบแยกต่างหาก

## 2. ขอบเขตและข้อห้าม
### อยู่ในขอบเขต
- ราคากลางและเวลาที่มีผล
- การเข้าสู่ระบบและสิทธิ์ตามบทบาท
- การสร้างเลขอ้างอิงการประเมิน
- ประวัติการประเมินและการเปลี่ยนแปลงแบบ append-only
- การยืนยันขาย การยกเลิก และการเชื่อมยอดจ่าย
- Dashboard และการแจ้งเตือนสำนักงานใหญ่
- การแยก DEMO / PILOT / PRODUCTION

### ห้ามทำ
- ห้ามใช้ค่าราคา DEMO เป็นราคาซื้อขายจริง
- ห้ามเชื่อถือราคาหรือยอดที่ส่งจาก browser โดยไม่ตรวจซ้ำที่ backend
- ห้ามเขียนทับหรือลบหลักฐานเดิมโดยผู้ใช้ทั่วไป
- ห้ามเปลี่ยนสูตรเดิม เช่น น้ำหนักมาตรฐาน การหักน้ำหนัก หรือส่วนลด โดยเป็นผลข้างเคียงจากการทำระบบ audit
- ห้ามถือว่าการประเมินเป็นธุรกรรมซื้อขายจนกว่าจะมีการยืนยันตามขั้นตอน
- ห้ามระบุว่าระบบป้องกันได้ 100%; การพูดราคานอกระบบหรือจ่ายเงินนอกระบบต้องใช้การควบคุมอื่นร่วมด้วย

## 3. โครงสร้างสภาพแวดล้อม
1. DEMO: ต้นแบบปัจจุบัน ใช้ข้อมูลจำลอง ไม่มีธุรกรรมจริง ไม่มีการส่งข้อมูลเข้าฐานข้อมูล production
2. PILOT: สภาพแวดล้อมทดสอบกับผู้ใช้/สาขาที่อนุมัติ ใช้ข้อมูลทดสอบหรือข้อมูลที่ผ่านการควบคุม ไม่เชื่อมการจ่ายเงินจริงจนกว่าจะอนุมัติ
3. PRODUCTION: เปิดใช้เมื่อผ่าน UAT, security review, ตรวจสูตรเดิม และอนุมัติจากเจ้าของระบบ

ต้องใช้ project/environment, credentials, database schema และ deployment แยกกันอย่างชัดเจน ห้ามนำ secret ของ production ไปใส่ใน client-side code หรือ repository

## 4. บทบาทและสิทธิ์
- พนักงานสาขา: สร้างการประเมิน ดูรายการของตนตามสิทธิ์ ยืนยันรายการที่ตนรับผิดชอบได้ตามนโยบาย ห้ามแก้ราคากลาง ห้ามลบ audit log
- ผู้จัดการสาขา: ดูรายการสาขาตน ตรวจรายการผิดปกติ อนุมัติกรณีที่นโยบายกำหนด ห้ามแก้หรือลบประวัติดิบ
- สำนักงานใหญ่/ฝ่ายตรวจสอบ: ดูข้อมูลข้ามสาขา ค้นหา ส่งออกรายงาน และจัดการกรณีตรวจสอบ ห้ามแก้หลักฐานต้นฉบับ
- ผู้ดูแลราคากลาง: เผยแพร่ราคาโดยมีแหล่งที่มา เวลาเริ่มมีผล ผู้สร้าง และผู้อนุมัติตามนโยบาย
- System administrator: จัดการระบบและสิทธิ์ แต่การเข้าถึงข้อมูลสำคัญต้องมี audit trail และไม่ควรสามารถลบหลักฐานโดยไร้ร่องรอย

ใช้บัญชีเฉพาะบุคคล ห้ามใช้บัญชีพนักงานร่วมกัน บังคับ session expiry และมีขั้นตอนเพิกถอนสิทธิ์เมื่อพนักงานย้าย/ออก

## 5. ข้อกำหนดด้านราคากลาง
- ต้องระบุแหล่งข้อมูลที่ได้รับอนุญาต ไม่ scraping แหล่งข้อมูลที่ไม่มีสิทธิ์
- เก็บ source/provider, source reference, fetched_at, effective_at, version, ผู้เผยแพร่ และสถานะการอนุมัติ
- ราคาที่ใช้คำนวณต้องถูกบันทึกเป็น snapshot ในแต่ละ evaluation เพื่อให้ตรวจย้อนหลังได้ แม้ราคากลางเปลี่ยนภายหลัง
- ถ้าราคาหมดอายุหรือดึงข้อมูลไม่ได้ ให้แสดงสถานะชัดเจนและใช้ขั้นตอนสำรองที่สำนักงานใหญ่อนุมัติ ห้ามแสดงราคาเก่าเสมือนราคาปัจจุบัน
- พนักงานสาขาห้ามแก้ราคากลางหรือส่วนลดมาตรฐาน
- หากมี override ที่ได้รับอนุญาต ต้องมีเหตุผล ผู้ดำเนินการ ผู้อนุมัติ และค่าก่อน/หลังครบถ้วน

## 6. ขั้นตอนการประเมิน
1. พนักงานเข้าสู่ระบบและระบบระบุ employee_id, branch_id, device/session และเวลา
2. สร้าง evaluation_id แบบไม่ซ้ำ และอ่าน snapshot ราคากลางที่ยังมีผล
3. กรอกประเภททอง น้ำหนักชั่งจริง และรายละเอียดที่จำเป็น
4. คำนวณที่ backend โดยใช้สูตรเดิมที่ได้รับอนุมัติ; browser แสดงผลเพื่อ UX แต่ไม่ใช่แหล่งความจริง
5. บันทึก inputs, formula_version, price_snapshot_id, calculated_amount และเวลา
6. เมื่อแสดงผลให้ลูกค้า ให้บันทึก customer_displayed_at และค่าที่แสดงจริง
7. หากแก้รายการ ให้สร้าง revision/event ใหม่พร้อมค่าเดิม ค่าใหม่ เหตุผล ผู้แก้ และเวลา ห้ามลบ revision เดิม
8. สถานะผลประเมินต้องแยกอย่างน้อย: DRAFT, DISPLAYED, ACCEPTED, DECLINED, EXPIRED, CANCELLED, CONVERTED_TO_TRANSACTION
9. ถ้าลูกค้าไม่ขาย ให้บันทึกเป็นผลประเมินที่ไม่เกิดธุรกรรม ไม่บันทึกเป็นยอดซื้อจริง
10. ถ้าลูกค้าตกลงขาย ให้ตรึง revision ที่ลูกค้าตกลงและสร้าง transaction_id เชื่อมกับ evaluation_id

## 7. ยอดจ่ายจริงและการกระทบยอด
- เก็บ agreed_amount, actual_paid_amount, payment_method, payment_reference, paid_at และผู้ยืนยันตามความเหมาะสมกับกระบวนการบัญชี
- actual_paid_amount ต้องมาจากหลักฐานหรือขั้นตอนยืนยันที่กำหนด ไม่ใช่ถือว่าเท่ากับ calculated_amount โดยอัตโนมัติ
- ถ้ายอดจ่ายต่างจากยอดที่ตกลง ให้ต้องระบุ reason code และผู้อนุมัติตาม threshold ที่สำนักงานใหญ่กำหนด
- สร้างรายงานประจำวันเพื่อเทียบ evaluation → accepted amount → actual paid amount → เอกสารรับซื้อ/บัญชี
- QR/เลขอ้างอิงบนใบประเมินควรพาไปตรวจข้อมูลจากระบบที่ต้องเข้าสู่ระบบหรือใช้ token ปลอดภัย ห้ามฝังข้อมูลส่วนบุคคลที่ไม่จำเป็นลง QR

## 8. Audit log
บันทึกเหตุการณ์อย่างน้อย:
- login/logout และการเปลี่ยนสิทธิ์
- สร้าง/แสดง/แก้ไข/ยกเลิก/หมดอายุการประเมิน
- ราคากลางที่อ่านและเวอร์ชันสูตรที่ใช้
- การยืนยันลูกค้าตกลงขายและการสร้างธุรกรรม
- การเปลี่ยนยอดจ่ายหรือข้อมูลสำคัญ
- การพิมพ์/ออกเอกสารและการส่งออกรายงาน เมื่อเกี่ยวข้องกับนโยบายตรวจสอบ

แต่ละ event มี event_id, occurred_at จาก server, actor_id, branch_id, entity_id, action, reason, before/after ที่เหมาะสม, request/correlation_id และแหล่งที่มา
- audit log เป็น append-only สำหรับบทบาทแอปพลิเคชัน
- จำกัดการเข้าถึงและบันทึกการเข้าถึงข้อมูล audit
- กำหนด retention และ backup ตามนโยบายองค์กร/กฎหมายที่เกี่ยวข้อง
- ป้องกันการแก้ไขย้อนหลังด้วยสิทธิ์ฐานข้อมูลที่จำกัด และพิจารณา hash chaining หรือ export สำรองที่ตรวจสอบได้สำหรับระดับความเสี่ยงสูง

## 9. การตรวจจับความผิดปกติ
ระบบควรสร้าง alert โดยไม่กล่าวหาว่าทุจริตอัตโนมัติ:
- มีราคาที่เสนอหรือยอดจ่ายต่างจากผลคำนวณ/ยอดตกลงเกิน threshold ที่อนุมัติ
- เปลี่ยนรายการหลังแสดงให้ลูกค้าดูหลายครั้ง
- ประเมินแล้ว DECLINED/CANCELLED บ่อยผิดปกติเมื่อเทียบกับรูปแบบงานและช่วงเวลา
- มีการ override ส่วนลด/ราคานอกช่วงสิทธิ์
- มีรายการยอดจ่ายจริงไม่ตรงกับเอกสารรับซื้อ
- พนักงานหรือสาขามีรูปแบบส่วนต่างผิดปกติเมื่อเทียบกลุ่มที่เทียบเคียงกัน

ทุก alert ต้องเก็บ rule_id, rule_version, triggered_at, severity, evidence references, review status และผู้ตรวจสอบ Threshold ต้องตั้งโดยสำนักงานใหญ่จากข้อมูลจริง ไม่ hardcode ตัวเลขตัวอย่างในเอกสารนี้เป็นกฎ production

## 10. โครงสร้างข้อมูลเบื้องต้น
- branches(branch_id, branch_code, name, status)
- employees(employee_id, auth_user_id, branch_id, role, status)
- price_snapshots(price_snapshot_id, provider, source_reference, fetched_at, effective_at, buy_rate, status, published_by, approved_by)
- formula_versions(formula_version_id, description, approved_at, checksum, status)
- evaluations(evaluation_id, branch_id, employee_id, status, created_at, displayed_at, current_revision_id, price_snapshot_id)
- evaluation_revisions(revision_id, evaluation_id, revision_no, input_json, formula_version_id, calculated_amount, displayed_amount, changed_by, changed_at, reason)
- transactions(transaction_id, evaluation_id, accepted_revision_id, agreed_amount, actual_paid_amount, payment_reference, paid_at, status)
- audit_events(event_id, actor_id, branch_id, entity_type, entity_id, action, occurred_at, reason, before_json, after_json, correlation_id)
- alerts(alert_id, rule_id, entity_id, severity, status, created_at, assigned_to, resolution_note)

เป็น logical schema สำหรับออกแบบเท่านั้น ต้องทำ migration review ก่อนสร้างในฐานข้อมูลจริง และไม่เก็บข้อมูลส่วนบุคคลเกินจำเป็น

## 11. ข้อกำหนดความปลอดภัย
- Authentication และ role-based access control ตรวจฝั่ง server
- ใช้ RLS เป็นชั้นป้องกันเพิ่มเติม โดยตรวจ branch_id และ role จาก identity ที่เชื่อถือได้ ไม่เชื่อค่า branch_id ที่ client ส่งมาเพียงอย่างเดียว
- ห้ามใส่ service-role key หรือ secret ใน frontend
- ตรวจ input และคำนวณจำนวนเงินฝั่ง backend ด้วย decimal/money-safe handling ที่กำหนดชัดเจน
- ใช้ TLS, secret management, backup และทดสอบ restore
- จำกัด export และบันทึกการ export
- ทดสอบสิทธิ์ข้ามสาขา, แก้ request, replay, duplicate submission, session expiry และการเรียก API โดยตรง

## 12. เกณฑ์รับมอบ (Acceptance criteria)
1. ผู้ใช้สาขา A ไม่สามารถอ่าน/แก้ข้อมูลสาขา B โดยไม่ได้รับอนุญาต
2. พนักงานทั่วไปแก้ราคากลาง ส่วนลดมาตรฐาน หรือสูตรที่อนุมัติไม่ได้
3. ทุก evaluation ที่แสดงต่อลูกค้ามีเลขอ้างอิงและ price snapshot/formula version
4. การแก้ไขทุกครั้งมี revision ใหม่และไม่ทำให้ revision เดิมหาย
5. กรณีลูกค้าไม่ขายปรากฏในประวัติการประเมิน แต่ไม่ถูกนับเป็นธุรกรรมซื้อจริง
6. ธุรกรรมจริงเชื่อมกับ revision ที่ลูกค้าตกลงและมียอดจ่าย/หลักฐานตาม workflow
7. ยอดที่ไม่ตรงกันสร้าง alert และติดตามผลการตรวจสอบได้
8. ผู้ตรวจสอบสำนักงานใหญ่ค้นหาและกรองข้ามสาขาได้ตามสิทธิ์
9. ทดสอบสูตรเดิมด้วย golden test cases ก่อน/หลังเปลี่ยนระบบแล้วผลเท่ากันทุกกรณีที่อนุมัติ
10. DEMO ไม่เขียนลง production และไม่มี credential production
11. ทดสอบ backup/restore และบันทึกผล UAT ก่อนเปิดใช้จริง
12. มีคู่มือเมื่อแหล่งราคากลางขัดข้องและมีผู้รับผิดชอบอนุมัติ

## 13. แผนดำเนินงาน
Phase 0 — ยืนยันสูตรเดิม, นโยบายราคากลาง, สถานะการอนุมัติส่วนลด และข้อมูลที่มีในระบบรับซื้อจริง  
Phase 1 — ออกแบบ data model, role matrix, threat model และ test cases; ยังไม่เปลี่ยนหน้าจอ production  
Phase 2 — สร้าง backend/API, authentication, audit log และ price snapshot ใน environment แยก  
Phase 3 — เชื่อมหน้า V2 ผ่าน API ใน branch/preview แยก โดยคงสูตรเดิม  
Phase 4 — ทำ dashboard และ alert สำหรับสำนักงานใหญ่  
Phase 5 — ทดสอบความปลอดภัย, UAT, สูตร, การกระทบยอด และทดลองสาขานำร่อง  
Phase 6 — เปิดใช้ production เมื่อผู้รับผิดชอบอนุมัติและมี rollback plan

## 14. ประเด็นที่ต้องได้รับคำตอบก่อนลงมือสร้าง production
1. ระบบรับซื้อจริงที่ต้องเทียบยอดคือระบบใด และมี API/export หรือไม่
2. ราคากลางที่องค์กรได้รับอนุญาตให้ใช้จริงมาจากที่ใด และใครเป็นผู้อนุมัติ
3. ส่วนลด 5% ในต้นแบบเป็นค่าทดลองหรือเป็นกฎจริง และมีข้อยกเว้นอย่างไร
4. ใครมีสิทธิ์อนุมัติส่วนต่าง และกำหนด threshold ตามนโยบายอย่างไร
5. ต้องเก็บข้อมูลและ audit log นานเท่าใดตามนโยบายบริษัท
